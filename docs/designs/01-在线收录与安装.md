# 01 · 在线收录与安装

日期：2026-11-02
状态：已定

依据：组织工作区 `README.md` 的仓库约定；GQY 主仓库 `docs/designs/04-插件运行时.md` 的 P3（manifest）、P9（安装）、P11（工具注册）；`docs/designs/11-安全与沙盒.md` 的 SEC5（安装即信任）。本仓库不复制主仓库的运行时协议，只引用。

## 范围

**做：**

- 一个公开、静态、可审计的在线插件目录 `registry.json`。
- 一个零第三方依赖的 Go CLI：浏览、搜索、校验、打包、安装、组织同步与外部提交。
- 静态网页目录：搜索、查看版本与一键复制安装命令。
- 发布流程：插件产物上传到 GitHub Release，目录只保存元数据、HTTPS 地址与 SHA-256。
- **来源分层自动化**：组织内公开插件仓库定时自动收录；组织外在线仓库一律通过自动生成的 PR 提交。

**不做（后置）：**

- 评分、评论、下载量、付费与账号体系。
- 自动更新、后台轮询、插件升级提示。
- 代码签名、供应链证明、镜像与 CDN。首版只做 SHA-256 完整性校验。
- 权限声明、运行时沙盒、安装前静态分析。沿用 GQY SEC5：安装插件 = 信任它。
- 运行时市场页面内嵌安装。CLI 与静态站独立，先不侵入 GQY 前端。

## 决定

### REG1 · 主目录可审计，发布目录由 workflow 生成

目录分两层，schema 完全一致：

- `main:registry.json`：可审计的基础目录。组织外插件的自动 PR 修改这里；CI 在这里跑 strict 校验与产物校验。
- `published:registry.json`：发布目录。`publish-catalog.yml` 在 main 基础上执行组织内同步后生成，CLI、网页与 Pages 以它为唯一线上入口。

发布目录由 `published` 分支提供 Raw 入口：`https://raw.githubusercontent.com/GQYTeam/gqy-plugins/published/registry.json`。`main` 的 ruleset 不需要给同步 bot 开后门，外部 PR 也继续受保护。

**为什么**：main 必须保留完整评审与状态检查；组织内自动收录又不能要求人工 PR。把“受保护输入”和“自动发布输出”分开，两个目标可以同时成立。

### REG2 · 产物不可变，目录只放 HTTPS 地址与 SHA-256

每个版本对应一份 `.tar.gz`。目录保存 `url`、`sha256`、`size` 与展示元数据。

- **组织外插件**只接受同一来源仓库的 GitHub Release 资产，URL 必须是 `https://github.com/<owner>/<repo>/releases/download/...`。
- **组织内插件**优先保留已发布的 Release 资产；没有 Release 时使用 commit SHA 固定的 GitHub tarball，不使用 default branch 归档。同一版本一旦登记产物，就不再覆盖；发现同版本不同产物只报告冲突并要求发新版本。

**为什么**：分支归档内容会变，哈希失去意义。Release 与 commit-pinned tarball 都是不可变的，`sha256` 才能成为安装前的硬闸门。

### REG3 · 身份是 `id@version`，最新版由三位数字版本排序决定

`id` 遵循 GQY P3 的 `^[a-z0-9][a-z0-9_-]{0,31}$`。版本固定 `MAJOR.MINOR.PATCH`。未指定版本时取最新非 `yanked` 版本；指定已撤回版本直接拒绝。

**为什么**：不引入 SemVer 预发布解析，先把可预测性做对；撤回不删历史，便于审计。

### REG4 · 目录元数据严格校验，未知字段拒绝

顶层 `schema_version` 固定为 `1`；时间用 RFC3339；`plugins` 必须是数组；插件 id 与版本不重复。JSON 解码拒绝未知字段，避免拼写错误被静默忽略。发布门禁额外使用 strict 模式：所有产物 URL 必须是 HTTPS 绝对地址。

**为什么**：目录是机器消费的协议，拼错字段应让 CI 红，而不是悄悄少一个插件。

### REG5 · 安装是“下载 → 哈希 → 安全解包 → 原子换目录”

安装目标固定为 `$GQY_HOME/plugins/<id>/`。流程顺序不可交换：

1. 解析 `id@version` 并选中目录条目。
2. 下载到插件目录内的临时目录，边下边算 SHA-256，并核对 `size`。
3. 拒绝路径穿越、绝对路径、符号链接、设备文件和超限包。
4. 校验包根 `manifest.json` 的 `id`、`version`、`mode`、`protocol`。
5. 解包到同文件系统的 staging 目录，最后 rename 到目标；覆盖时先备份旧目录，失败则回滚。

**为什么**：先校验后执行、同盘 rename 保证不留下半个插件。安装是本地写文件，不经过 shell。

### REG6 · 默认只安装，不自动加载

成功安装后默认不调用 `load`。可以显式传 `--server` 让 CLI 调用 `/api/plugins/reload`，再传 `--load` 才请求加载。

**为什么**：GQY P9 约定安装后默认不加载；加载会真正启动第三方进程，必须作为单独的用户意图。

### REG7 · CLI 零第三方依赖，支持 Go 1.22+

`cmd/gqy-plugin` 只使用标准库，提供 `list / search / info / install / verify / package / version`。目录读取支持 HTTPS、`file://` 与本地路径，便于离线与测试。

**为什么**：GQY 主仓库是 Go 标准库工程；工具链不能比宿主更重。`go run ...@latest` 即可从任何已装 Go 的机器运行。

### REG8 · 静态站零构建、只读发布目录

`web/` 是原生 HTML/CSS/ES modules，`fetch('./registry.json')` 渲染卡片与安装命令。没有后端、没有数据库、没有直接提交入口。

- `publish-catalog.yml` 每次构建时运行组织内同步，生成 `published` 分支并部署 Pages。
- 机构外收录由 issue / workflow_dispatch 触发 `external-plugin-pr.yml`，只生成 PR，永不直接写 `main`。
- 人工仍可提 PR，但外部来源必须走自动 PR 审核链路。

**为什么**：目录发布频率低，静态站足矣；把“生成发布目录”和“评审主目录”拆开，站点不引入后台与写权限。

### REG9 · 外部发布走 PR，CI 是门禁

- 组织外插件必须走自动 PR，PR 只改 `main:registry.json`，CI 至少执行 `gofmt`、`go vet`、`go test`、`go build`、`node --check` 与 strict 目录 / 产物校验，合并前人工确认来源与许可。
- 组织内插件由 `publish-catalog.yml` 自动同步到 `published` 分支；`published` 规则只做删除保护与禁止强推，内容完全由工作流生成。

**为什么**：哈希保证下载完整，但保证不了来源本身可信；外部代码的最终信任来自评审。组织内代码已有组织治理，可走自动发布。

### REG10 · 安装即信任，哈希只防传输篡改

`sha256` 不证明发布者身份，也不提供签名。插件安装后以 GQY 进程同等权限运行，能读写文件与联网。首版只在文档、站点与 CLI 输出里明确边界，不做权限墙。

**为什么**：与主仓库 SEC5 一致；把“哈希校验”误读为“安全沙箱”比不做更危险。

### REG11 · 来源分层：组织内自动收录，组织外一律自动 PR

目录条目的 `source_type` 只有两种合法值：

| 来源 | 发现方式 | 写目录方式 |
| --- | --- | --- |
| `org` | 定时扫描组织下公开的 `gqy-plugins-*` 仓库 | `publish-catalog.yml` 校验后生成 `published:registry.json` 并部署 Pages |
| `external` | issue 表单或 `workflow_dispatch` 提交仓库与 Release 产物 | `external-plugin-pr.yml` 校验后自动创建 PR，必须 CI + 人工评审后才可合入 `main` |

`gqy-plugin add-external` 会拒绝 `GQYTeam` 仓库，防止组织内插件绕过自动收录；`sync-org` 只处理组织内仓库。`repository` 字段保存来源仓库，`source_type` 供站点和审计识别。

**为什么**：组织内仓库已经被组织治理与 CI 覆盖，可信成本低，自动化收益大；组织外代码没有同等的组织控制，必须保留人工评审闸门。

### REG12 · 内自动、外 PR 的权限落地

- `main` ruleset：删除保护、禁止强推、要求一次 PR 评审、要求 `Check (Go 1.22.x)` 与 `Check (Go stable)` 通过；仅仓库管理员保留应急 bypass。
- `published` ruleset：删除保护、禁止强推；只允许工作流正常 fast-forward 写入。
- `external-plugin-pr.yml` 只推功能分支并创建 PR，没有合并步骤，也没有自动合并配置。
- `publish-catalog.yml` 不需要写 `main`，只用 `GITHUB_TOKEN` 写不受 PR 评审约束的 `published` 输出分支，并部署 Pages。

**为什么**：组织内自动收录与外部评审闸门必须同时成立，但不能靠扩大 main 的 bypass 面来换取自动化。

### REG13 · 组织内同步的版本冲突处理

同步器扫描每个 `gqy-plugins-*` 仓库的默认分支 HEAD，下载 commit-pinned tarball，解析 `manifest.json` 并计算真实 SHA-256 / size。

- 目录已有同 id 同 version：保留旧产物不覆盖；若 URL / SHA-256 不同，结果里报告冲突。插件所有者必须 bump version。
- 新 version：追加到 `versions`，按数字版本降序。
- 目录已有外部条目同 id：拒绝把来源类型改为 org，避免来源混淆。
- 缺少 manifest 的仓库、私有仓库、归档仓库和 fork 跳过并记录原因。

**为什么**：自动同步不能破坏“同版本产物不可变”；版本号是唯一的发布边界。

## 验收

1. `make check` 全绿，`registry.json` 通过 strict 校验。
2. `gqy-plugin list` 能显示目录中的至少三个组织内插件与最新版本。
3. `gqy-plugin package` 对同一插件目录重复打包得到相同 SHA-256。
4. `gqy-plugin verify --artifacts` 能逐一下载并校验 Release 产物、大小与包内 manifest。
5. `gqy-plugin install` 安装后目标目录结构正确；重复安装无 `--force` 报错；`--force` 覆盖不残留备份。
6. 篡改产物、错哈希、路径穿越包与 `mode:"oneshot"` 安装均被拒绝。
7. 静态站加载 `registry.json` 后能搜索、展示版本并复制安装命令；卡片安装命令必须先 `go install` CLI，再 `gqy-plugin install ... --server ... --load`。
8. `gqy-plugin sync-org` 能发现组织内公开插件、跳过无 manifest 仓库、追加新版本并保留已登记产物。
9. 外部收录 issue 触发 `external-plugin-pr.yml` 后只出现一个自动 PR，`registry.json` 的 `source_type` 为 `external`；该 workflow 不包含直接 push main 或自动合并。
10. `publish-catalog.yml` 能从 main 生成 `published:registry.json`，`published` 分支可 fast-forward 更新且禁止强推/删除；CLI 默认 URL 指向该分支。
11. 外部 PR 的 CI 由 workflow 显式 dispatch，合入后 Pages 自动重新生成发布目录。
12. oneshot 卡片显示 `ONESHOT` 且不提供常驻安装按钮。
